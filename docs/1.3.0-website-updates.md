# 1.3.0 — the website's updates of 8–11 November, and its look

Date: 12 November 2026. App version 1.3.0, data schema 3.

The website (tehqeqatehadees.com, repository `hadithsearch`) changed its
narrators, its search and its copied text between 8 and 11 November 2026.
This release brings those changes into the app and dresses the app like the
website. As with 1.2.0, two rules held: **the app stays as fast as before**,
and **no reader downloads the whole collection again**.

### Not brought over (and why)

- **Mixed-digit numbers, number search in every digit form, footnote marks**
  (6644044, 40b25a8). They were merged into a branch that was itself reverted
  (#108/#109) and never reached the website's `main`, so the live website does
  not have them.
- **The study's own PDF pages** on a narrator's page. The website does not let
  the app's domain ask for them (no CORS), as with 1.2.0's narration pages.
- **«انہی روایات کے دیگر روات»** (related narrators). Small, and not needed to
  read a narrator; left for later.

## 3. Data: schema 3 without a new download

`narrators` gains `arabic_name` and `excerpt` (from `/api/narrators`, which
already had them). The builder now **upgrades a schema-2 build in place**
(`FIRST_UPGRADABLE_SCHEMA`): it opens the published snapshot, migrates it and
writes the new registry, keeping the epoch and cursor. On a device, migration
2 → 3 adds the two columns and forgets the registry's checksum, so the next
sync downloads only the registry.

An app still on 1.2 sees `schema_version: 3` in the manifest, stops before
syncing and updates itself (as it already did for `min_app_version`).

Tried against the live website from the published build: `fullBuild: false`,
cursor unchanged (`1794074990786:2`), registry changed, nothing else fetched.

## 4. Measurements

Measured on 12 November 2026 on the live data (910 narrations, 317 narrators),
Node's SQLite on a laptop, median of 5. A phone is slower in absolute terms;
the comparison holds.

**Search** (old = 1.2's phrase / all words / any word)

| Query | Results before → after | Time before → after |
|---|---|---|
| «نماز» | 161 → 161 | 53 → 38 ms |
| «روایت» | 830 → 830 | 205 → 145 ms |
| «کا» | 910 → 910 | 164 → 99 ms |
| «خطبہ جمعہ» | 64 → 6 | 70 → 30 ms |
| «نماز کی فضیلت» | 891 → 206 | 102 → 102 ms |
| «ابان بن ابی عیاش» | 605 → 54 | 256 → 258 ms |
| «رسول اللہ ﷺ نے فرمایا» | 910 → 747 | 105 → 199 ms |

The first version of the new search took up to 17 s: SQLite ran the scoring
query again for every row. `MATERIALIZED` subqueries, sorting ids before
reading any text, and the count taken with the page fixed it. A long query of
common words is still slower than before, and still under the old slowest.

**Narrators:** list 8 ms, one narrator's studies 11 ms.

## 6. Development

`pnpm dev` could not do a first download: Vite's dev server sends a `.gz` file
as gzip-encoded, the browser unpacks it, and the checksum fails. The dev server
now sends `data/*.gz` as it is, like GitHub Pages (`rawSnapshots` in
`apps/web/vite.config.ts`).
