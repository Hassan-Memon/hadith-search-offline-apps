# 1.2.0 — bringing the website's November updates into the app

Date: 7 November 2026. App version 1.2.0, data schema 2.

The website (tehqeqatehadees.com, repository `hadithsearch`) gained chapters,
a book registry, narrator pages, new reader tools and a part-2 preface on its
تعارف page between 4 and 7 November 2026. This document records what of that
the app now has, how it gets the data, what it costs in size and speed, and
what was left out.

Two rules held throughout: **the app must stay as fast as before**, and **its
download and storage must stay about the same size**.

### Not brought over (and why)

- **Arabic and English interface.** Every screen's text would need three
  versions; worth doing as its own change. `packages/i18n` is ready for it.
- **«Google Docs» button.** The Word file already opens in Google Docs.
- **Noto Naskh Arabic font** (94 KB). The app keeps its current Arabic font to
  keep the install size level.
- **Urdu line spacing fix.** The app already used tall line spacing (2.2), so
  Nastaliq was never clipped here.
- **Admin screens** (book/chapter registry editing, narrator preview). Website only.

## 2. How the data gets to devices

The website is still not changed. The hourly GitHub Action
(`packages/core/src/build/data.ts`) makes three extra small requests per run:

| Request | Gives |
|---|---|
| `GET /api/books` | 16 books: order, part no., date, aliases, PDF coverage |
| `GET /api/chapters` | 69 chapters: name, heading, order, description |
| `GET /api/narrators` | 338 narrators: name, aliases, death note/year/century |
| `GET /api/narrators/<slug>` | only for a narrator whose entry changed (see below) |

From requests it already made:

- **The list** (`/api/all-hadees/<page>`) now carries each hadith's `chapter`
  and `authored_at`. Moving a hadith to another باب does not change its
  `updated_at` on the website, so the builder compares these two fields with
  its copy and sends the difference as a small `meta` entry
  (`{id, chapter, authored_at}`) in the change file. No detail request needed.
- **The detail** (`/api/hadees-detail/<id>`) now carries `narrators`:
  `[{slug, name, start, end}]`, meaning sections `start`…`end` of this
  narration are the study of that narrator. The builder keeps
  `{slug, start, end}`; the name comes from the registry.

**Narrator changes without an edit.** The website rebuilds its narrator
index when its heading reader improves, without editing the narration. The
builder keeps a signature of each narrator's index entry (name, study and
narration counts, length) in `narrator-signatures.json`, a file only the
builder reads. When a signature changes, it asks `/api/narrators/<slug>` for
that narrator's narrations and fetches those again. More than 40 changed
narrators in one run means every narration with narrators is fetched again.

**Published files** (new ones marked ★):

```
data/manifest.json                    + "registry": { "url", "sha256" }
data/snapshot-<sha16>.sqlite.gz       now also holds books, chapters, narrators
data/changes-<epoch>-<n>.json         { items, deleted, meta★ }
data/registry-<sha16>.json ★          { books, chapters, narrators }
data/narrator-signatures.json ★       builder only; devices never read it
data/announcements.json, data/files.json
```

**On the device** (`packages/core/src/sync/engine.ts`): change files apply
`meta` entries along with documents. The registry is downloaded only when
`manifest.registry.sha256` differs from the one the device stored
(`settings.registry_sha256`). A new device gets it inside the snapshot.

**PDF pages.** The website does not allow the app's domain to ask whether one
narration's pages are known (no CORS). So the link appears only for books
where every narration has its pages (`pdf_pages_count >= count` in the
registry): 9 of the 16 books today. Other books still have «ویب سائٹ پر کھولیں».

## 3. Database: schema 2

`packages/core/schema.sql`, `user_version = 2`:

- `hadith.chapter` (slug) and `hadith.narrators_json` (`[{slug,start,end}]`),
  **placed before the large text columns**. SQLite stores a row's columns in
  order, so a column after `html_content` can only be read by walking through
  the whole narration text. With the old order, narrator queries took ~50 ms;
  with this order, ~15 ms. Index `idx_hadith_chapter`.
- New tables `books`, `chapters`, `narrators`, and a view `book_spelling`
  (each spelling of a book → the book's name).
- Migration 1 → 2 (`src/db/migrate.ts`) adds the two columns with `ALTER`
  before `schema.sql` runs. Devices on 1.1 install the new snapshot anyway,
  because the first schema-2 build starts a new epoch.
- A book filter resolves the book's spellings first, then uses a plain
  `book IN (…)`. A subquery inside the search query made filtered searches
  2–4× slower.

New queries in `src/db/repo.ts`: `listChapters`, `getChapter`,
`chapterSamples`, `getBook`, `bookSpellings`, `listNarrators`,
`narratorTotals`, `getNarrator`, `narratorStudies`, `hadithNarrators`,
`replaceRegistry`, `updateHadithMeta`; `listHadith`, `searchHadith` and
`relatedHadith` take a `chapter`.

## 6. Deploying

- Merge to `main`. The first build is a full one: about 910 detail requests,
  one at a time, ~7.5 minutes (the workflow allows 30). Later runs are as
  before plus three registry requests.
- Every device downloads the snapshot once (~9.5 MB). Bookmarks, history and
  dismissed announcements carry over.
- The data requires app 1.2.0 (`min_app_version`), so installed 1.1 apps
  update themselves before syncing.

## 7. Updating devices that run 1.0

Found after the first deploy: browsers and installed apps that had 1.0 open
did not switch to 1.2, while a new browser got 1.2 at once.

**Why.** The app's own code is updated by its service worker.

- In 1.0 (`registerType: 'autoUpdate'`), a new worker takes over by itself and
  the page reloads when it does.
- Since 1.1 (`registerType: 'prompt'`, `src/update.ts`), a new worker waits
  until the page sends it `SKIP_WAITING`, so a reader is never reloaded in the
  middle of a narration.
- A 1.0 page never sends that message. So the 1.2 worker waited until every
  window of the app was closed. Reloading a tab does not count, and a phone
  keeps an installed app alive in the background, so in practice it never
  switched.

**Fix.** `apps/web/public/sw-handoff.js`, loaded into the generated worker
(`workbox.importScripts` in `vite.config.ts`):

1. When the new worker installs and an older one is active, it asks every
   open page for its version (`postMessage` with a `MessageChannel`, 1.5 s
   timeout).
2. Pages of 1.2 and later answer (`answerVersionQuestions()` in
   `src/update.ts`).
3. If any page does not answer, it is 1.0, and the worker calls
   `skipWaiting()`. The 1.0 page sees the new worker take over and reloads
   itself into 1.2, which is what 1.0 always did.
4. If every page answers, the worker waits as designed: it is applied when the
   app goes to the background, or from the «ابھی اپ ڈیٹ کریں» banner.

**Tested** in a headless browser with a server whose content can be swapped
like a deploy:

- 1.0 installed and in control → swap to 1.2 → reload: the page was on 1.2
  (version `1.2.0`, six home cards) one second later, with nothing waiting.
- 1.2 open → swap to a newer build → update check: same page, not reloaded,
  new version waiting, banner shown.

**For readers still on 1.0:** the new version is picked up the next time the
app is really opened. On a computer, reloading the tab is enough. On a phone,
close the app from the recent apps list and open it again. It then switches by
itself within a second or two.

## 8. Notes for development

- `vite preview` sends `.gz` files with `Content-Encoding: gzip`, so the
  browser unzips the snapshot and its checksum fails locally. GitHub Pages
  sends `application/gzip` and works. Use `pnpm dev` or a plain static server
  to test a first install.
- On Node versions before 26, run the tests by file:
  `node --test packages/core/dist/test/*.test.js`.
- `src/export/` is copied from the website (`frontend-next/src/lib`), with
  only `!` assertions added for this app's stricter TypeScript. Keep the two
  in step when the website changes its export.
